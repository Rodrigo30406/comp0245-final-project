### Sanity check result — the expert cannot hold its command for 20 ms (02:05)

`runs/diagnostics/expert_hold20_validation_20261027/summary.json`: with the
expert's own command recomputed every step but APPLIED only every 20 steps
(held in between), **0/205 success, all `stalled`, median final EE distance
1.97 m**. The joint PD at kp = 100, kd = 30 on a 1 ms loop does not tolerate a
20 ms zero-order hold. Consequences:

- Action holding / action chunking at 20 ms is not a viable protocol for this
  task; the decision-rate variant (queue item 8) is answered negatively
  without further runs.
- The GRU was redesigned before training: the memory (GRU state) updates every
  `stride` steps, but the output head reacts at every 1 ms step from the
  current features plus the latest memory. Stride only changes how often the
  memory looks; the control period stays 1 ms for every policy compared.
- First GRU attempt (action held at stride 20; 1 ms variant with 32-episode
  batches) was discarded: undertrained (about 3 000 updates) and one run hit
  CUDA OOM while nine jobs shared the GPU. Relaunched with 8 episodes per
  batch, chunk 250 memory updates at stride 20 and 1000 at stride 1,
  validation in batches of 8 episodes.

| GRU, memory every 1 ms | 0.089 | 0 / 0 / 0 | 5.91 m | 3 | 0.56 / 0.27 |

Memory made closed-loop control worse, not better, at equal offline error.
The likely mechanism is the one DART targets: once the learned policy's
actions deviate, the recurrent state itself is driven off the training
distribution and the error compounds through the memory as well as through
the robot state. Teacher-forced training of a recurrent policy on expert
trajectories never shows the network a hidden state produced by its own
mistakes. The MLP cannot accumulate such a state. This is a single-seed
negative result; it is preserved as such. The GRU trained on DART-low data
(noisy trajectories, clean labels) is the direct test of that mechanism and
is in evaluation.

## Conclusions of the night

1. **Offline error does not predict closed-loop success.** The 21-input GRU
   with 1 ms memory has the second-best offline error of the night (0.086)
   and zero arrivals; the best closed-loop policy has an offline error of
   0.124 (on noisier validation data). Model selection for this project must
   be done on closed-loop arrivals, which is what
   `scripts/evaluate_policy.py` measures.
2. **The baseline fails for two separable reasons**, and the night isolated
   each: (a) its inputs do not expose where the goal is relative to the
   robot or how far the episode has progressed, so it cannot resolve the
   expert's hidden phase (privileged ablation: −38 % error with the hidden
   state; egocentric + clock: 0 → ~60 arrivals); (b) it is only ever shown
   expert-perfect states, so its own small errors push it off-distribution
   and the commands saturate (DART: clipping 0.80 → 0.00, runaway gone).
3. **Fixing both gives a policy that reaches half the validation goals**
   (stable arrival = within tolerance for 0.5 s; 100 of 205 at 5 cm, 49 at
   1 cm) with nothing but the 21 observations the slides prescribe, a
   per-episode clock, and the goal pose, all available at deployment.
   Parameter count is unchanged (21 k). Correction added in the morning
   follow-up: "stable arrival" does not mean the policy stays. At 40 s only
   63 of the 205 episodes are still within 5 cm and none within 1 cm; see
   the seed-replication section for the hold problem.
4. **Memory (GRU) and observation windows did not help** in closed loop, at
   equal or better offline error, with or without DART. The consistent
   pattern (slower memory more stable than faster memory; window MLP worst
   runaway) points to the policy's own deviations being integrated into the
   history. These are single-seed negative results and are recorded as such;
   they do not rule out recurrent policies trained with on-policy
   corrections (DAgger), which was outside tonight's budget.
5. **Noise level matters.** DART low (σ 0.5 / 1.0) is the sweet spot of the
   two levels tried; medium noise destroys too many demonstrations
   (46 % expert failures) to help.

### Why the DART-low GRU ends 2–4 m from every goal (trace analysis)

Rodrigo asked whether the 2–4 m cluster meant the GRU stops short. It does
not. Per-episode traces of
`runs/evaluation/dart_low_gru_egocentric_on_clean_validation_20261027`
(shoulder position vs base goal, wheel commands, arm pose), 205 episodes,
percentiles 10 / 50 / 90:

| Quantity | GRU 25 ego, memory 1 ms, DART low |
|---|---|
| Minimum base-to-goal distance | 0.9 / 1.7 / 3.4 cm |
| Time of that minimum | 2.7 / 5.0 / 7.7 s (expert base arrival median 7.3 s) |
| Base-to-goal distance at 40 s | 2.7 / 3.3 / 3.6 m |
| Base speed, last 5 s | 0.90 / 1.14 / 1.25 m/s |
| Base path length (expert: 1.1 m) | 17.5 / 18.6 / 20.1 m |
| EE distance from base, whole episode | 1.01–1.03 m (arm never leaves its initial posture) |
| Base still moving at 40 s | 205 / 205 |

So the GRU **navigates correctly and arrives at the base goal on time**
(within 2 cm). What fails is everything after: the wheel command does not go
to zero. The base drifts backward for a few seconds (small negative wheel
commands around 12–20 s), then accelerates forward again with slowly
increasing wheel commands (0.3 → 1.6 rad/s) and is at 1.1 m/s when the
horizon ends. The arm torques never produce a reach: the end-effector stays
about 1.02 m from the base for the entire 40 s. The 2–4 m "cluster" is where
a slowly accelerating base is after 35 s, not a stopping point; the spread
is small because every episode follows the same profile.

Interpretation: the expert's behaviour at the goal is "wheels zero, raise the
arm", gated by its internal `nav.done` flag. The GRU's hidden state never
flips into that regime. Having arrived, it keeps producing navigation-like
wheel commands with a growing bias, and once the base leaves the goal region
the history looks like nothing in training and the drift feeds itself. This
is the compounding-through-memory mechanism, now observed directly: the
failure begins exactly at the phase transition the memory was supposed to
capture.

The same signature appears in the 36 failed episodes of the DART-low
egocentric MLP (minimum base distance 9 cm, path length 20 m, base speed
1.0 m/s in the last 5 s): the MLP has the same post-arrival failure mode, but
only in 18 % of the goals instead of 91 %.

Conclusions:

1. **Keeping the lecturer's 21 inputs and adding the 10 relative geometry
   features is the single most effective change of the project.** It lifts
   the plain MLP from 9 to a median 138 of 205 arrivals (with DART) and
   removes the need for memory: the 32-input MLP equals both GRUs at
   arriving and is the best of all four at staying (final within 5 cm
   median 38 against 17 and 11 for the GRUs), with a quarter of the
   parameters and the lowest seed variance.
2. **Memory stopped paying once the inputs were right.** With the 25
   egocentric inputs the GRU doubled the MLP's arrivals; with the 32 inputs
   the two architectures tie at arriving and the GRU holds worse. The GRU's
   earlier advantage was compensating for missing information in the input,
   not something intrinsic to recurrence.
3. The recommended model is therefore the **32-input MLP trained on DART-low
   data**, seed 3 if one checkpoint must be picked
   (`runs/training/mlp_dart_low_raw21plus_seed3`: 137 arrivals, 96 still
   within 5 cm at 40 s, 92 held ≥ 10 s, median final 6 cm), with the
   five-seed spread reported alongside.
4. Holding remains the open problem for every recipe (expert: 205 / 205
   final within 5 cm). The latched "arrived" input is still the candidate
   fix, now to be tried on the 32-input MLP.
