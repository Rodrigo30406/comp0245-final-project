[Methodology] Reproducibility
-----------------------------
- The dataset is generated deterministically by collect_data.py: the same command + the same --seed produces exactly the same data.
- Randomness has two layers:
  1) batch level: rng = default_rng(--seed); all targets, and which episodes get noise, are drawn once at the start.
  2) episode level: episode_seed = --seed * 100000 + episode index, which determines only the noise sequence inside that episode.
- The seed is tied to the episode index rather than having all episodes share one random-number stream:
  when running in parallel, the order in which episodes finish is not fixed; tying the seed to the index guarantees that each episode's result
  is independent of the run order and of the number of workers; any single episode can also be re-run on its own for debugging.
- Each episode runs in a brand-new process (Pool maxtasksperchild=1),
  starting from a clean pybullet state, so one episode cannot affect the next.
- Each run saves all command-line arguments to config.json; the meta of each .npz records the
  target, noise parameters, seed, stop reason and final error; index.csv summarises all episodes.
- Expert parameters are imported from robotnik_arm_task.py rather than copied, which guarantees that the recorded expert is exactly identical to the template.
- Verification: for target (0, 1.1, 0.5), the output of collect_data.py and that of the original robotnik_arm_task.py agree item by item
  (identical base trajectory and end-effector error; both reach the target at t = 8.00 s with a final error of 0.0021 m).
- Notes / limitations:
  * pybullet DIRECT mode is deterministic on the same machine with the same version; a different machine or version may give tiny floating-point differences.
  * The simulator's built-in sensor noise (noise_flag in robotnik_arm.json, currently 0) uses the
    unseeded global np.random. If it is turned on, an additional seed must be set to reproduce results.
- Example command for regenerating a dataset (run under final/robotnik_arm_task/):
  pixi run --manifest-path <RoboEnv>/pixi.toml python collect_data.py --n-episodes N --workers 8 --noise-frac 0.3 --seed 0 --out-dir data/run1


[Introduction] Problem formulation
----------------------------------
- Behaviour cloning: take the expert's (state, command) pairs as supervised-learning data (the expert is the template's base_controller + arm_controller, a model-based classical controller),
  train a regressor to replace the expert, and deploy it in closed loop.
- Input X: base_pos (xy), base_bearing (encoded as sin/cos), arm q / qd, wheel qd, target (x, y, z).
  Wheel joint angles (unboundedly accumulating and unrelated to the task) and the fingers (held fixed) are not used as inputs.
- Output Y: base (v, w) + 7 arm joint torques.
  With the skid-steer structure the 4 wheel speeds have only 2 degrees of freedom ([rw, lw, lw, rw]); predicting (v, w) guarantees
  that the wheel speeds on the left and right sides are consistent, and the output dimension is also lower.
- The target has position only, no orientation: the expert's IK uses only the translational part of the Jacobian, J[:3].


[Methodology] Data collection design
------------------------------------
- The expert runs sequentially: the base navigates first (align -> drive -> orient), and only after navigation finishes (or hits the 25 s timeout) does the arm start to reach.
  During navigation the arm still outputs "hold pose" torques (PD + gravity compensation), not 0.
- There are 4 phase labels in total (align / drive / orient / reach). After done = True, the phase of BaseNavState is still
  "orient", so nav_done is used separately to identify reach.
- Hidden states (q_des_arm, phase, nav_done) are also recorded, reserved for experiments on "whether extra inputs are useful";
  note that the expert is absent at test time, so using these quantities requires stating how they would be obtained at test time.
- DART-style noise: execute "expert command + noise" and store the clean expert command as the label, so that the data contain "how to correct after deviating".
  The noise is re-drawn every 0.3 s (piecewise-constant): 1 kHz white noise would be averaged out by inertia and would barely move the robot.
  Base noise is added only during the navigation phase: after navigation finishes the expert no longer moves the base, so it cannot correct drift at that point.
- Labels use the clean expert command rather than "command + noise": the noise is independent of the current state, so the model cannot predict it from X;
  and in a state that has been pushed off course, the clean label is exactly the expert's corrective action. The noise determines only "which states to visit"; the label determines "what to do".
- The X and Y recorded at each step are from the same instant: the state is a snapshot read before Step (np.array / .copy() copies the data);
  if the sensors were re-read after Step, X would become the state at time t+1.
- The target is sampled uniformly in cylindrical coordinates (r, theta, z) (azimuth, distance and height each correspond to different expert behaviours).
- Targets that are very close, or directly above the vehicle body: the expert never reverses (v >= 0); instead it turns around 180° in place, drives forward, and turns around again.
  Measured: (0, 0, 1.0) is reached at 11.4 s, (0.25, 0, 0.5) at 10.5 s. Docking point = target - standoff * (direction from the origin pointing to the target).
- The ceiling of behaviour cloning is the expert: behaviours the expert cannot perform (e.g. reversing) have no demonstration data, so the model cannot learn them either.
  The regions where the expert fails are defined as outside the task scope (neither the training set nor the test set contains them), and this is stated explicitly as an assumption.
- Random initial pose: the base start position is sampled uniformly within a disc of radius R around the origin (rho = R*sqrt(u), uniform by area),
  and the heading is sampled uniformly within a given range. Implementation: after creating the simulation, reset it with resetBasePositionAndOrientation,
  without modifying the shared config file.
  The target is sampled relative to the start pose (r and theta with the start heading as 0°) and then converted to world coordinates; the input X still uses world coordinates.
- Modification to the expert (to be stated in the README): the docking direction is changed from "from the world origin toward the target" to "from the robot's initial position toward the target".
  When the start is at the origin this is exactly identical to the template (verified: identical to the original output item by item).
- A problem with the template's check_stop: it checks "stalled" first (error improves by < 2 mm within 3 s) and "reached" afterwards.
  If the base hardly needs to move (r ≈ standoff 0.65 m), the arm reaches the target early and sits on it waiting for min_time = 8 s,
  and at 8 s it is wrongly reported as "Target not reachable" (the final error is in fact only 0.000-0.001 m).
  Fixed in collect_data.py: whenever the final error is < 10 mm, the episode is recorded as reached.
- Self-collision (collision_enable) is kept off, for the following reasons:
  * With it on, the base cannot turn in place: during the align phase the left and right wheels rotate in opposite directions, yet the vehicle drives straight at about 0.3 m/s, and has covered about 7 m by the 25 s navigation timeout;
    the default target was not reached even after running the full 40 s step cap. The base parameters (e.g. wheel_base_width) were calibrated with collisions off.
  * With it on, there is already contact in the initial pose: the collision bodies of the arm base link_base and the vehicle body base_link overlap to begin with.
  * pybullet's collision detection is automatic: it first does a coarse filter with AABB bounding boxes, then accurately computes the contact points between convex collision bodies
    (position, normal, penetration depth), and finally the constraint solver computes the contact forces and friction forces.
    Collisions between the robot and the ground are always on; the switch controls only collisions between the robot's own parts.
  * limitation: the arm may pass through the vehicle body; targets very close to the body should be checked in the GUI, or avoided at sampling time.
- Train/val/test are split by episode: adjacent samples at a 1 ms step are nearly identical, so splitting by time step would cause data leakage,
  and would also fail to measure generalisation to new targets.


[Results / Observations] First run (target 0, 1.1, 0.5)
-------------------------------------------------------
- 8.0 s in total (8000 steps): align 0-2 s, drive 2-4 s, orient 4-4.6 s, reach 4.6-8 s.
- About 57% of samples are in the navigation phase (arm held still) - there is a phase-imbalance problem.
- StopCriteria.min_time = 8 s: even if the target is reached early, the run lasts at least 8 s, so there is a stretch of stationary samples at the end of the episode.
- The base stops about 6 cm from the standoff goal (pos_tol = 0.08); the remaining error is compensated by the arm.
- final_error cannot measure the arm's accuracy (the earlier explanation "noise causes about 9.9 mm" was wrong):
  for episodes longer than 8 s, the run stops as soon as the error is < 10 mm, so the recorded final error always lands right around 10 mm;
  only episodes that reach the target within 8 s continue converging to 2-5 mm. The median error of clean episodes is likewise 10.0 mm.


[Results] Expert workspace (data/probe: 200 clean episodes, r 0.1-4 m, theta in all directions, z 0-1.6 m)

[Methodology / Results] Noise-magnitude experiment (same seed, 40 identical targets and start points, r 0.1-3, z 0.2-1.2, start radius 2 m)
---------------------------------------------------------------------------------------------------------------------------------------------
  Base noise (sigma_v, sigma_w)                   Reached   Nav timeout
  No noise                                        38/40     2
  0.05 m/s, 0.2 rad/s, no decay                   29/40     11
  0.05 m/s, 0.2 rad/s, with decay                 28/40     11
  0.03 m/s, 0.1 rad/s, with decay                 37/40     3
  0.02 m/s, 0.05 rad/s, with decay (new default)  40/40     0
- Failure mechanism: as the base approaches the docking point it is pushed off by the noise and misses the target; the expert's steering rate limit in the drive phase is only 0.3 rad/s,
  and it does not go back to the align phase to turn in place, so it circles around the docking point, the circles growing larger, until the 25 s navigation timeout.
  sigma_w = 0.2 rad/s is already 2/3 of the maximum steering capability in the drive phase, so the expert has no spare capacity to correct.
  -> Conclusion: the noise must be clearly smaller than the expert's control capability in that phase; otherwise what is collected is bad demonstrations that "even the expert cannot recover from".
- Decaying the noise only near the target (within 0.5 m) did not help: the heading had already been pushed off before entering the decay zone.
- With the new default the noise is still effective: compared with the clean version of the same episode, the median of the maximum deviation of the base trajectory
  during the navigation phase is 3.1 cm (maximum 15.9 cm), and the median of the maximum joint deviation during the arm-holding phase is about 2.3°.
- The decay of the arm noise (within 0.15 m of the end effector from the target) is retained on principle; this experiment did not measure any quantifiable effect
  (final_error is affected by the stopping rule, see above).
- Failures of the expert on clean episodes were also observed: with random start points, 2/40 navigation timeouts (cases very close to the target that need a large turn-around).
  During training, episodes that were not successful are filtered out by the status in index.csv.
- Another physical phenomenon: the wheels' lateral friction coefficient is only 0.01 (anisotropicFriction); if navigation times out during a high-speed turn,
  the vehicle body keeps sliding sideways after the wheels stop (measured about 0.2 m/s, lasting several seconds).


[Methodology] Collection efficiency
-----------------------------------
- 20 parallel processes: 40 episodes take about 0.7 min (about 1 episode/s); 200 episodes take about 3.4 min (16 processes).
- Storage: about 2-2.7 MB/episode (1 kHz full recording, float32 compressed).
- Long collections can be interrupted and resumed (--resume): episodes that are already saved are skipped, and resuming is refused if the dataset parameters are inconsistent;
  index.csv is written as collection proceeds.


[Methodology / Results] Final datasets
--------------------------------------
- Common settings: r 0.1-3.0 m, theta in all directions, z 0.2-1.2 m, start point random within a radius of 2 m, heading random;
  noise sigma_v = 0.02, sigma_w = 0.05, torque 2.0 N*m, with decay.
  * data/train: seed 1, 2000 episodes, 50% with noise; used for training and validation (the validation set is split by episode).
  * data/test: seed 100, 300 episodes, no noise; used only for the final evaluation.
  * data/pilot: seed 1000, 100 episodes, used for trial runs.
- Training set: 4.71 GB, 21.6 million samples (1 kHz, about 6 hours of robot running time); no NaN; wheel-speed label structure all correct;
  torque saturation fraction 0.15%; median episode length 9.4 s.
- Expert success rate: training set clean 98.4%, noisy 91.6%, overall 95.2%; test set 298/300 = 99.3%.
  The expert's success rate on the test set is the upper bound / reference baseline for the learned model.
- Failure analysis: of the 97 failures, 96 are navigation timeouts, and 94 of those are circling: the base gets as close as about 9 cm to the docking point
  (just outside pos_tol of 8 cm), and then circles farther and farther away.
  The failures are concentrated in "short-distance driving": for noisy episodes the success rate is 74.8% for r < 0.46 m and 77-84% for r 0.83-1.55 m;
  for r > 1.55 m it is close to 100%. The median distance from the start to the docking point for these episodes is only 0.48 m.
  Cause: short-distance driving does not have enough straight segments for the heading to settle, plus the limited steering capability in the drive phase (0.3 rad/s),
  and the expert does not go back to turning in place. This is a limitation of the expert itself (clean episodes also have 1.6% failures), not a problem with data collection.
- Filtering rule: keep only episodes with status == reached and nav_timed_out == False.
  After filtering there is somewhat less noisy short-distance data (about 75% retained); this is a slight coverage bias and needs to be stated in the report.
- Phase proportions (before filtering): drive 49.4%, reach 27.2%, align 16.7%, orient 6.7%.
  Episodes that fail by circling inflate the proportion of drive, so this should be recomputed after filtering.
- At 1 kHz adjacent samples are almost identical: during training one can downsample (e.g. take 1 step out of every 10-20).
  Learning curves should use the number of episodes, not the number of samples, as the x-axis.
- Expectation: the model will inherit the expert's failure mode (circling on short-distance drives). At evaluation, stratify by r and compare with the expert's success rate on the same test episodes.

[Methodology] Evaluation protocol v1 (pre-registered: written on 2026-10-28, before any learned model was evaluated)
--------------------------------------------------------------------------------------------------------------------
Code: evaluate_policy.py; documentation: EVALUATION.md. The following rules stay unchanged in all later comparisons.
If they need to change, bump the version number (v2) and re-run all earlier baselines.

1) Evaluation sets: all collected from the clean expert, with the same task distribution as train/test.
   - DEV (seed 200, 300 episodes): all development-stage decisions are made here, including model selection, data configuration and hyperparameters.
   - HARD (seed 201, r 0.1-1.6 m, 200 episodes): distance from the start to the docking point <= 1.15 m, the region where the expert and the noise experiments fail most easily.
     The primary metric of the noise experiments is computed here.
   - CONFIRM (seed 202, 300 episodes): each adopted change is replicated here once, after the decision has been made.
   - test (seed 100, 300 episodes): used only for the final report, opened only once at the very end, and takes no part in any decision.
   Rationale: if test is used to select models, test becomes a validation set, and the estimate of generalisation will be optimistic.
   For example, for several models of truly equal ability, picking the one with the highest score on test makes the reported success rate on average 1.5-2 percentage points too high
   (at n = 300 the standard error of a single estimate is about 1.7 percentage points), and this bias cannot be seen from the results themselves.
   Confirmed with teammates on 2026-10-28: so far nobody has used data/test to make any decision, and test is still sealed.
   Offline comparisons (e.g. MSE) likewise may only use the validation set held out by episode from train, not test.
2) The simulation setup is exactly identical to data collection: 1 kHz, ground friction 1.0, wheel contact and friction parameters, motor gains (400, 30),
   fingers fixed, start pose set by reset. Arm torques are clipped to +-30 N*m for all policies (the expert's clipping value).
3) The definition of success is identical for the expert and learned models, and does not depend on the expert's internal state (nav_done, phase):
   - success: at some time within 40 s the EE error is < 10 mm, and the episode ends normally (stop_reason == reached);
   - after reaching the target, the simulation continues for 1 s: settled means the error stays < 15 mm throughout this 1 s; hold_error is the mean error during this 1 s, used as the precision metric;
     an error raised or NaN output within this 1 s also counts as a failure;
   - early termination (only to save compute; it must not turn an episode that would otherwise have succeeded into a failure):
     stalled: for 5 consecutive seconds all of the following hold: base speed < 1 cm/s, angular velocity < 0.02 rad/s,
              every arm joint < 0.05 rad/s, EE error has not improved by 1 mm, error > 30 mm.
              When the error is within 30 mm it is never judged as stalled, because a slow final approach can still succeed;
     tipped: roll or pitch > 0.5 rad; as well as invalid output (NaN) and policy errors (policy_error).
   - The early termination itself must also be validated:
     Expert: validation passed (see [Results] below).
     Each new model family: run once on DEV with --no-early-stop, to confirm that no episode judged stalled
     would have succeeded without early termination; record the result here. Policies that use t as an input always use --no-early-stop.
   - Design record: the initial stall rule was 3 s, 2 mm, with no 30 mm floor. Code review found that it could misjudge as failures learned models that
     "approach the last 2 cm very slowly but are still converging" (the expert covers this stretch quickly, so it could not be detected).
     Before any learned model was evaluated, it was changed to the current rule.
   The template's check_stop is not used: it depends on nav_done, has an 8 s minimum time, and checks "stalled" before "reached".
4) Method of comparison:
   - All policies run the same batch of episodes, and are compared in pairs, episode by episode, against the expert (and between models).
     Report the 2x2 table, the conditional success rate (the fraction of the episodes in which the expert succeeds where the model also succeeds), the exact McNemar test,
     and the confidence interval of the difference obtained from a bootstrap paired by episode.
   - Success rates come with Wilson 95% intervals. Resolution: at n = 300, about +-2.5 percentage points near a 95% success rate and about +-3.4 near 90%;
     at n = 100 about +-4.5 and +-6 respectively. So differences of 1-3 percentage points are basically unresolvable.
     When a difference is not significant, write "no difference detected at a resolution of about X percentage points".
   - Models with training randomness are trained with at least 3 seeds. For each episode, first average the success rate over seeds, then bootstrap over episodes,
     and also list the per-seed differences. Do not pool several seeds into a single McNemar test (the episodes are the same batch, which would be pseudoreplication).
   - The stratified analysis uses d0 = r - standoff(z) (the signed distance from the start to the docking point, the mechanism variable of expert failure), not r.
   - When several variants or several strata are compared together, use Holm correction.
5) Rule for adopting a change (before each experiment starts, write out the specific thresholds here):
   the lower bound of the confidence interval of the primary-metric difference > 0; the improvement appears where the hypothesis predicts it (failure mode or stratum);
   other strata do not get noticeably worse; the direction is consistent on CONFIRM. When these are not met, keep the original setting and record the result honestly.
6) Record template for each experiment, with the first half filled in before looking at the results:
   ID / date | question | hypotheses and competing hypotheses, with the predictions of each (including mechanism predictions) | the only variable changed |
   fixed: data, filtering rule, number of retained episodes, features, downsampling, hyperparameters, evaluation sets, protocol version |
   primary metric, minimum detectable difference | adoption rule | budget
   -> Result: difference, 95% CI, per-seed differences, mechanism metrics -> Conclusion: supported / not supported / inconclusive -> Next step.
   Result files: results/<run>/ (rollouts.csv, summary.txt, config.json, which contains the git commit).

[Methodology] Step 2, data-layer analysis: pre-registration (written 2026-10-29, before running the analysis on data/train)
---------------------------------------------------------------------------------------
Code: analyze_dataset.py; output: results/data_analysis/ (summary.txt, episodes_{train,dev,hard}.csv, figures).
This step trains no model and makes no adoption decision; it only produces descriptive quantities, mechanism evidence, and the tools and pre-written predictions needed for Steps 3 and 4.
1) Data and unit of analysis
   - All 2000 episodes of data/train (1897 after filtering), plus the clean expert recordings of DEV and HARD. CONFIRM and test are not touched.
   - The unit of analysis is the episode: per-sample quantities are first summed within each episode; CIs use an episode-level bootstrap (2000 resamples),
     resampling within the clean / noisy strata so that the proportion of the two is unchanged. Descriptive proportions are not bootstrapped.
2) Data already seen before pre-registration (recorded honestly)
   - train: ep 0-199 (initial look: phase sequence, |q_des - q|, end-effector error at nav_done); ep 0-59 (the earlier copy-baseline R²);
     the plan-review agent, to verify claims, looked at several of ep 0-120 and ep 1900-1907 (copy-window error, label variance, lag-k, chatter,
     displacement during align, etc.); the index.csv of train/DEV/HARD (mode retention rate, n per stratum, fraction filtered out with an align turn angle > 170°);
     and the full-set statistics already in this file (phase proportions, filtered counts stratified by d_goal, etc.).
     -> Predictions are tested on the "unseen" subset: train ep 200-1999 with 1900-1907 removed; results over all episodes are reported as well.
   - data/pilot (seed 1000, 100 episodes, independent): used to calibrate the analysis parameters and to test the code end to end. Results relevant to the predictions
     were already seen on the pilot (see the items below), so the test on train is an independent replication of the pilot observations, not a blind test.
   - test / CONFIRM: during the plan review, a review agent, while listing config.json files in a loop, mistakenly read data/test/config.json and
     data/confirm/config.json. It read only the sampling settings (seed, ranges), which are identical to those in EVALUATION.md; it read no episode,
     index.csv or result. The sealed status is unaffected.
3) Code verification (on the pilot, before running train)
   - An independent agent, working only from the written definitions and without looking at the script, recomputed the per-class step counts, the copy-baseline RMSE, the inconsistency counts of the restart expert (three variants),
     the chatter index, the j6 clamping fraction, the torque jump at the start of reach, and the event-locked error curves: all agree with the script (counts identical one by one, RMSE to the 6th decimal place).
   - Arm IK recomputed with the same algorithm as arm_controller: on the pilot, 99.98% of reach steps differ from the recorded qd_des by < 1e-3 rad/s.
4) Parameters calibrated on the pilot and not changed afterwards
   - Post-event window = settling time: the part of the post-event copy error that exceeds that event class's own steady state (the level 400-500 ms after the event);
     from some moment on, it does not exceed the steady state itself for 50 ms continuously (curve <= 2 x steady state), capped at 0.4 s.
     start 0.127 s, align>drive 0.055, drive>orient 0.234, drive>reach 0.072, orient>reach 0.380, noise resampling 0.
     Design note: the initial definition, "peak decays by 90%", covered only the spike at the event step (1-2 ms); afterwards the error was still about 10 times the steady state and lasted tens of ms;
     it was changed to the present definition before looking at train. The main result uses the event-locked error curves; the window fraction is a secondary number; a sensitivity analysis with fixed window widths of 50/200/400 ms is also given.
   - Chatter step: deviation of the torque from the mean of the preceding and following steps (maximum over joints) > 1 N·m. On the pilot, the magnitude is continuously distributed from 0.001 to 60 N·m with no gap,
     so a fixed value far above smooth control (about 0.001 N·m per step) is used; the mechanism test is repeated at 0.3 and 3 N·m.
   - wheel-speed rule threshold: a measured forward speed > 0.065 m/s counts as being in drive (on the pilot, 0.15% of align steps exceed it and 0.03% of drive steps do not).
   - Arm high/low grouping at z = 0.45 m (on the pilot, chatter is almost entirely below it).
5) Descriptive quantities (not predictions, and not counted toward "confirmation")
   Mode table (M0 |d0| < 0.08, M1 d0 <= -0.08, M2 d0 >= 0.08, and the 0.08 <= |d0| < 0.15 boundary band), phase proportions
   (per sample / per episode, before and after filtering, clean / noisy), copy-baseline error and its decomposition, event-locked error curves,
   task-space coverage (7 dimensions in world coordinates vs 3 dimensions relative to the start, train LOO vs DEV / HARD), label quality
   (j6 start angle out of range, torque jump at the start of reach, saturation, chatter index by z).
6) Prediction 1: which parts of the base labels are not a function of the current observation ("restart expert": every 10 steps, call base_controller with a fresh FSM state
   and compare with the label; |dv| > 0.02 m/s or |dw| > 0.05 rad/s counts as inconsistent).
   The main test uses the "standoff point computed from the current position" (single-frame information only); the secondary test uses the true standoff point (looking only at FSM memory).
   - 1a Inconsistency is concentrated in drive and orient: (share of drive+orient among the inconsistent steps) / (share of drive+orient among all steps), CI lower bound > 1.
   - 1b Concentrated in episodes with |d0| < 1: ratio of inconsistency rates (|d0| < 1 / |d0| >= 1), CI lower bound > 1.
   - 1c After adding the wheel-speed rule, the inconsistency within drive is at least halved: ratio CI upper bound < 0.5 counts as supported, lower bound > 0.5 as unsupported, otherwise inconclusive.
   - 1d Essentially unchanged within orient: ratio CI inside [0.8, 1.25]. This is almost determined by construction (during in-place turning the measured forward speed is about 0, so the rule has no effect).
   Competing hypotheses: inconsistency uniformly distributed (ratio about 1); the wheel-speed rule does not help (1c ratio about 1).
   Already seen on the pilot: main tests 1a (1.20) and 1b (2.64) hold, 1c does not hold (ratio 1.00: the inconsistency in drive comes from the direction of the standoff point,
   which depends on the start position that is not in the input, rather than from FSM memory), 1d holds; in the true-standoff-point version 1b (9.6) and 1c (13.7% -> 0%) hold, 1a is inconclusive.
7) Prediction 2: mechanism of the torque-label chatter. On unseen filtered episodes that have chatter steps:
   - H-limit (the IK joint-limit freezing loop toggles back and forth at every step): the fraction of chatter steps with a joint within the limit margin has CI lower bound >= 0.8,
     and is enriched relative to the non-chatter reach steps of the same episodes (ratio CI lower bound > 1); mechanism detail: the fraction in which the set of frozen joints differs from the previous step is enriched (CI lower bound > 1).
   - H-singular (damping near singular configurations): the fraction of chatter steps with sigma_min < 0.15 has CI lower bound >= 0.8, and is enriched.
   Already seen on the pilot: H-limit holds (93.7%, enriched 1.6-fold; frozen-set switching enriched > 70-fold, mainly j2, j6), H-singular does not hold (sigma_min was never < 0.15).
8) Prediction 3 (exploratory, because rough proportions were glimpsed during the plan review): within 0.08 <= |d0| < 1 (M0 has no align segment, excluded),
   logistic regression of expert failure (being filtered out) on noisy + M1 + rcs(|d0|, 4 knots) + align turn angle + noisy:align turn angle,
   with an LR test on the two align terms (alpha = 0.05). The mechanism chain (align turn angle -> displacement during align -> distance deviation at the start of drive) is descriptive only.
   The pilot has only 48 episodes and 5 failures and is uninformative (all 5 are on the side with align turn angle >= 127°; recorded only).
9) Written in advance for Steps 3 and 4 (before seeing any model result)
   - Candidate closed-loop failure categories and their expected locations: (a) never departs (H-copycat); (b) circles around the standoff point (same as the expert, concentrated at small |d0|);
     (c) turn-direction ambiguity: the required in-place turn is > 160° (|theta| > 160° in M2, |theta| < 20° in M1, and the roughly 180° orient at the end of M1),
     MSE regression will average left and right turns to w about 0, appearing as no turning in place or swinging back and forth; (d) phase flicker at nav_done: the learned model has no latch,
     so the arm may begin to extend before the base has settled, or extend and then retract; (e) arm instability at low targets (z < 0.45) (the labels have chatter).
   - Step 3: offline torque error, and closed-loop settled / hold_error, reported separately for z < 0.45 and z >= 0.45; strata with n < 30
     (DEV M0 and boundary band, HARD M2 >= 1) are descriptive only.
   - Competing hypotheses for the Step 4 qd_wheel ablation: H-copycat (with qd_wheel, lag at start-up and at stopping: does not depart, or overshoots the standoff point);
     H-hidden-phase (without qd_wheel, align and drive cannot be told apart: turns through large angles while driving, concentrated at small |d0|);
     H-goal (from Prediction 1 on the pilot): with or without qd_wheel, the steering error in drive is concentrated in episodes that deviate from the start-target line
     (noisy, large drift during align), because the single-frame input does not contain the start position.
   - Step 4 stride sweep: add "average within the window, then subsample" as a control (the low-z torque labels have a period-2 chatter, and direct subsampling aliases);
     the event step itself accounts for about 35-45% of the excess post-event copy error (pilot), and at stride s the probability of that step being kept is only 1/s.
   - Coverage of test: when test is finally unsealed, it is computed with the same code.

[Methodology] Step 3: training pipeline and deployment (train_policy.py, bc_features.py, policies/)
-------------------------------------------------------------------------------
1) Data and split (trained/data_split.json, shared by all models and all training seeds)
   - data/train, 1897 episodes after filtering (status == reached and nav_timed_out == False, asserted in the code).
   - Split by episode 85% / 15%, stratified by noisy x mode (mode_of(d0)), n_val = round(0.15 n) per stratum, split seed 0:
     1613 training episodes, 284 validation episodes (validation clean M0/M1/M2 9/23/121, noisy 8/18/105).
   - Stride 9 (odd: at low z the torque labels alternate in sign step by step, and an even stride would alias; Step 2). Each training episode has one start offset
     (0-8, default_rng(0)), training rows = steps offset::9, 1,764,684 rows in total. The offset seed and the split seed are both 0, and the two rngs produce the same
     stream, but the offset is unrelated to episode content and does not affect the results (recorded honestly: the plan said "an independent data seed").
   - Validation rows = all 1 kHz steps of the validation episodes, 2,802,594 rows (the event step accounts for 34-51% of the post-event excess error, and downsampling would drop it).
   - Cache results/step3/cache (one .npy per column, memory-mappable, lossless relative to the recording, 762 MiB); the cache and each model record the sha256 of the split file,
     and refuse to load on a mismatch.
2) Features and outputs (bc_features.py, the same function for training and deployment)
   - ego (22): the target's dx, dy in the current body frame, target z, planar distance rho, cos/sin beta, arm q(7), qd(7), v̂, ŵ;
     ego_novw (20): v̂, ŵ removed; raw (23): base x, y, sin/cos yaw, q(7), qd(7), v̂, ŵ, target x, y, z.
     All are pure transforms of the current observation: no t, no expert rules, no start pose. (The feature set ego_novw_ee of experiment D in Step 4 additionally uses the robot
     kinematic model in info, computing the end-effector position by forward kinematics from the current q and base pose; still no t, start pose or expert rules; see the Step 4 pre-registration.) v̂, ŵ are converted from the measured wheel speeds by the skid-steer model (average of the front and rear wheels on each side).
   - 9 outputs: (v, w) + 7 torques (clean labels: wheel_cmds, torque_arm, not the noise-perturbed executed commands); standardised by the mean and standard deviation of the training rows,
     with the 9 outputs equally weighted in the loss. At deployment, collect_data.wheel_speeds(v, w) converts back to the 4 wheel speeds.
3) Models
   - MLP 2x128 ReLU: sklearn 1.9.1 MLPRegressor (Adam lr 1e-3, alpha 1e-4, batch 200, shuffle), one partial_fit call per epoch,
     random_state = np.random.RandomState(seed). Verified: each partial_fit is exactly one epoch, the Adam state is preserved, the shuffle differs in every epoch
     (an int random_state would make every epoch replay the same permutation), and the same seed is bit-identical across processes. float64, single thread, each seed in its own process, run in parallel.
   - early stopping: standardised MSE over all 1 kHz steps of the validation set; an epoch counts as an improvement only if the loss falls by >= 1e-3 relative to the last significant improvement; patience 5, at most 200 epochs;
     the weights of the epoch with the lowest validation loss are saved.
   - OLS: least squares on standardised features plus an intercept (np.linalg.lstsq), stored as a one-layer model. At N = 1.76M, Ridge with alpha <= 1e3 is no different from OLS.
   - Model file .npz: weights, standardisation parameters, feature description, meta (hyperparameters, split hash, loss curve, code sha256, etc.); deployment uses a numpy forward pass.
4) Verification (unit tests tests/test_training.py, test_policies.py, test_hybrid.py, all passing)
   - (a) The numpy forward pass vs MLPRegressor.predict (after de-standardisation): maximum difference < 1e-9; the same for OLS.
   - (b) (v, w) -> wheel speeds -> (v, w) round trip: maximum difference < 1e-12.
   - (c) ego / ego_novw features are invariant (< 1e-9) under any planar rotation + translation of the base and target; raw is not (control).
   - (d) Sign convention: in pybullet, w = +0.5 rad/s for 1 s gives yaw +0.512 rad (-0.510 at -0.5); in the pilot, in 40/40 clean M2 episodes,
     the first nonzero w label has the same sign as beta at t = 0.
   - (e) Training / deployment consistency: the BCPolicy.act output for a single observation agrees with the vectorised training path on 300 recorded steps (< 1e-9), tested for all 3 feature sets.
   - Randomly sampled rows in the cache are bit-identical to the raw .npz values (including noisy episodes: the labels are the clean commands, not the executed ones).
   - Training determinism: ego seeds 0-2 were first used for the pilot, then retrained with the final code (only the offline lag analysis changed), and checked to be bit-identical to the models used for the pilot (results below).
5) Cost: for the ego MLP, a single process takes 6.3-6.8 s per epoch of partial_fit + 2.9 s for the validation loss; with 10 processes in parallel, about 15-50 s per epoch (competing with evaluation for CPU);
   the 3 pilot seeds stopped at 21-26 epochs (best epoch 16-21). The OLS fit takes 1.2 s. About 1.2 GB of memory per process.
   Inference: BCPolicy takes about 20-30 us per step (mostly the overhead of single-row feature construction), closed-loop policy_ms has a median of 0.12-0.17 ms, the expert 0.19 ms.
6) Definitions for the offline analysis (descriptive, trained/<name>.offline.json)
   - RMSE / nRMSE of each output, by phase class (align, drive, orient, reach_move, reach_hold), clean / noisy, inside vs outside the event window,
     compared with the copy baseline (measured v̂, ŵ as the prediction of (v, w)); torques by segment (navigation hold, reach_move, reach_hold) x z (< / >= 0.45 m).
   - Lag k within the event window: k from -30..30 steps, k > 0 means the prediction lags the label (pred[t] ~ label[t - k]); all k use the same set of t
     ([event - 20 ms, event + settling time]); when t - k < 0 the label is padded with 0 (the robot starts from rest), and beyond the end of the episode it is padded with the last value;
     a curve with relative range < 1e-3 is marked "flat" (no k given), and |k| = 30 is marked as the boundary. Only clean validation episodes.
     Design note: the initial version searched only k >= 0 and used a different set of t for each k; review found that a lead would be reported as 0 and the k of the start event would be too large;
     corrected before looking at any offline MLP result. ego-ols: for start, align>drive and drive>orient, v and w all have k = +1, the same as the copy baseline.
   - drive>reach has only 2 clean events in the validation set, so its lag is unreliable.


[Methodology] Step 3: closed-loop failure taxonomy (analyze_rollouts.py) and criterion validation (before looking at any learned model's DEV/HARD results)
-----------------------------------------------------------------------------------------------------
1) Final decision order (each failed episode is assigned to exactly one class; successes are not classified)
   1. crash: tipped, invalid_action, policy_error (harness_error is an error of the evaluation program: rerun it; it does not count as a policy failure).
   2. no_start: the start is >= 0.15 m from the docking ring, and base path < 0.15 m and cumulative turning < 10 degrees (decided before the
      "approached" test).
   3. Never approached (minimum docking-ring distance > 0.3 m): runaway (final ring distance > start ring distance + 1 m) -> no_progress (ring
      distance never got smaller than at the start by more than 0.10 m: it turned but did not drive toward the ring) -> never_other.
   4. Approached: circling (cumulative turning - align_req - orient_req (orient_req counted only if docked) > 360 degrees) -> left_or_overshot
      (final ring distance > 0.3 m) -> parked_no_arm (arm_extend_time is empty, |min_error - navdone_ee_err| < 2 cm, and navdone_ee_err
      >= 7 cm) -> extended_not_reached (1 <= min_error < 5 cm) -> approached_other.
   - Failures whose start is < 0.15 m from the ring (like M0) are never no_start; when the base does not move they are additionally tagged no_motion_near_ring and reported separately.
   - The fraction of wheel speeds exceeding the expert envelope is descriptive only and plays no part in the classification.
   - Merged classes (for plotting; they also correspond to Rodrigo's 4 classes): arrive_stay = success and held_10s; arrive_leave = success but not held for 10 s;
     base_ok_ee_not = parked_no_arm + extended_not_reached + approached_other; base_not = no_start + runaway + no_progress +
     never_other + circling + left_or_overshot; crash.
2) Amendments relative to the plan (design record; the reasons all come from cases with known answers, the expert or the zero policy; only no_progress comes from the ego pilot)
   - circling: the plan subtracts align_req + orient_req. The expert's 2 M1 failures (DEV 169, HARD 124) never docked the base, so it never did the 180-degree
     orient turn; under the plan they computed only 209-219 degrees of excess turning and were classed as left_or_overshot. After changing to count orient_req only when docked, 14/14 are classed as circling.
   - no_start: in the plan, "start within 0.15 m of the ring is excluded" can never take effect in the never-approached branch (a start <= 0.3 m from the ring already counts as approached), so the
     no_start motion test is moved before the approach decision (for episodes whose start is >= 0.15 m from the ring). The path threshold was changed from 0.05 m to 0.15 m: the zero policy's
     arm collapses under gravity and pushes the base by 0.008-0.108 m (turning <= 0.22 degrees); with 0.05 m, 25 of 280 were missed.
   - parked_no_arm gained navdone_ee_err >= 7 cm: "short-reach" episodes where the hold posture at expert docking was already less than 7 cm from the target (DEV 38, HARD 12);
     with min_error one cannot tell "did not extend" from "extended but did not reach", and the original rule would fire on 5 expert-success episodes. Failures on these episodes are counted separately in each class table.
   - no_progress (new): on the pilot, ego's failures were mostly "turn in place to align, then never drive forward again" (path 0.13-0.30 m, turning about 90-100 degrees), which neither satisfies
     not starting (turning > 10 degrees) nor is a runaway, and would formerly have fallen into never_other. This class was added after looking at ego's behaviour on the pilot (recorded honestly); the
     criterion is mechanism-independent and applies equally to both sides.
   - The plan's "expert arm_extend_time and nav_done differ by < 0.2 s" cannot hold (see protocol v1.1); changed to report the distribution only.
3) Validation results (results/step3/validate.txt; expert v1.1 DEV + HARD + CONFIRM, zero policy DEV)
   - (i) All 14 expert failures are classed as circling (excess turning 370-399 degrees, minimum ring distance < 1 mm: circling around the docking point). PASS.
   - (ii) Zero policy: all 280 failures whose start is >= 0.15 m from the ring are classed as no_start; the 20 whose start is < 0.15 m from the ring are approached_other,
     all carrying the no_motion_near_ring tag. PASS.
   - (iii) 786 expert successes: the failure criteria fire on only 5 documented exceptions: HARD 19, 158 and CONFIRM 62, 69 are genuine "arrive after circling"
     (the expert circled until the 25 s navigation timeout, then docked and still reached, with 397-596 degrees of excess turning); DEV 11 starts close enough to the target that the base barely moves
     (path 0.08 m) and the arm arrives at 1.57 s. The other criteria (including parked_no_arm) never fire on successes. PASS (documented exceptions).
   - (iv) The expert never extends the arm before nav_done (0 of 679 episodes with an arm extension). PASS.

[Methodology] Step 3: statistical methods (analyze_rollouts.py)
----------------------------------------------------
- The success rate of a single seed uses a Wilson interval. The seed mean uses a two-level bootstrap (first resample seeds with replacement, then episodes, 10000 times, percentile CI);
  trials from several seeds are not pooled into one Wilson interval (pseudo-replication).
- Paired difference between the two sides: in each draw, seeds are resampled independently within each side, and episodes are drawn only once and shared by both sides (paired), difference = B - A; two-sided p = 2 min(P(<=0), P(>=0)).
- Calibration (simulation done during review, null hypothesis, E = 300): with S = 5 and a seed standard deviation of 11 percentage points, the two-level percentile bootstrap has P(p < 0.05) = 0.115 and
  P(CI lower bound > 0) = 0.068 (nominal 0.025); with a seed standard deviation of 20 percentage points, 0.087 / 0.050; with a seed standard deviation of only about 2 percentage points (binomial noise only)
  P(p < 0.05) = 0.003 (too conservative). Unit-test simulation (S = 5, E = 100): bootstrap 0.093 / 0.048, Welch t-test on per-seed success rates
  0.052 / 0.030. Reason: with only 5 seeds, resampling seeds underestimates the variance at the seed level, and the percentile interval is too narrow.
  -> Condition (1) of experiment A requires the lower bound of the two-level bootstrap CI to be > 0 and also the lower bound of the Welch 95% CI on per-seed success rates to be > 0; in experiment B, the comparison with the expert cell
     (deterministic, no seeds) uses a one-sample t-test on the per-seed differences, and Holm uses the larger of the bootstrap p and the t-test p.
- Exact McNemar for each pair of seeds (descriptive), all seed x seed differences; seed consistency: Cochran Q, normalised psi = psi_raw / (1 - prod p - prod (1 - p)).
- Holm: reject if p_adj <= alpha. Comparison families: the 3 comparisons of experiment B form one family; the strata form one family, containing only strata with n >= 30 (DEV: M1 48, M2 0.08-0.5 46,
  M2 0.5-1.0 56, M2 >= 1.0 138; M0 12 and the boundary band 8 are descriptive only); the secondary metrics form one family. The main comparison of experiment A is decided on its own, with no correction.
- Integrity checks: paired runs must come from the same evaluation set, with complete and identical episode sets; the comparison is refused if there is any harness_error; runs of hybrid policies must
  have used --no-early-stop (otherwise the ME cell would be biased low by the stall rule).

   - The specific prediction for ME in the pre-registration was written on the premise of "adopting ego" (the base does not start); what was actually adopted is ego-novw, so this item does not apply.
   - EM: written in the pre-registration as an open question, with Rodrigo's E1 predicting that the arm does not extend: supported (1500/1500 do not extend).
   - The main bottleneck for the next step is therefore the arm's trigger: in a single-frame input there is no reliable cue that "it is time to start extending" (in the training data the expert's trigger comes from its own FSM
     memory nav_done, see the orient / reach confound in prediction 1 of step 2). Candidates (after step 4, needing a new pre-registration): give the model an observable trigger feature
     (e.g. base stationary and on the ring), or split the base and the arm into two models, with an explicit switching rule computable from the observations; the latter amounts to handing the expert's

8) Limitations stated in advance
   - C3 only changes the weighting of the training rows: the added k0 frames are states the expert actually visited and actually labelled, with no synthetic labels, and only qd gets jitter. It targets
     the covariate shift of "the learner stopping in a state the expert almost never passes through (base already stopped, arm not yet moved)", which is a problem of the kind addressed by DAgger (Ross, Gordon, Bagnell, AISTATS 2011) and
     DART (Laskey et al., CoRL 2017), but without querying the expert for new states (see [References]).
   - The copies also make every epoch longer (with batch 200 the number of Adam steps per epoch +1.5% / +5.8% / +23.4%), while patience and early stopping count in
     epochs: K changes both the weight of the trigger states and the number of optimisation steps per epoch (the validation set and the stopping rule are unchanged).
   - C3-EM's expert base gives perfect docking, so it is a diagnostic only.
   - The probe r is an offline necessary condition and does not guarantee a closed-loop trigger; closed-loop conclusions come only from DEV/HARD/CONFIRM.
   - K is chosen on the validation set, not on DEV.
   - The learned trigger is an observable rule and may fire earlier than the expert's (H-premature).

1) The only variable: the input features
   - Feature set ego_novw_ee (23 dimensions) = ego_novw (20 dimensions) + 3 near-field truncated end-effector error components, model name ego-novw-trig-ee:
     e = target - ee_pos (world coordinates); e_c = e · min(1, 0.10 / |e|) (length clipped at 10 cm, direction unchanged);
     (ee_dx, ee_dy) = the horizontal component of e_c rotated into the current base yaw frame, ee_dz = the z component of e_c.
     Reason for truncation: in the training rows |e| has mean 0.72 m and standard deviation 0.69 m; with per-column standardisation, an untruncated 16 mm error is only 0.02-0.06 standard deviations, while after truncation
     1-2 cm is 0.17-0.59 standard deviations (differing by column for ee_dx / ee_dy / ee_dz). Information from far away is already given by ego_dx, ego_dy, target_z, rho.
   - Everything else is the same as ego-novw-trig: training rows, split, stride 9, K = 16 trigger-frame copies (the same σ_hold and jitter seed; the e_c of the copies uses the recorded ee_pos at step k0,
     and the jitter changes only qd), standardisation using only the original training rows (also for the new columns), network, hyperparameters, early stopping, validation set.
   - The input dimension changes, and the initialisation and the early-stopping trajectory change with it (the same confound as item 5 of the C3 results), so the attribution is written as
     "the end-effector error features and their effect on training".
   - End-effector position: training uses the recorded ee_pos (computed by the expert at every step with pinocchio, at the same step as base_pos, base_ori, q_mes); at deployment BCPolicy takes dyn_model and ee_frame_id
     from info at reset, and at every step makes the same calls as the expert (ReoderJoints2PinVec(base_pos, base_ori, q_mes) ->
     forwardKinematics -> updateFramePlacements -> oMf[ee]). It uses the full base pose (including tilt): D = explicit forward kinematics + tilt information (effect on the end-effector
     position: median about 5 mm, maximum about 10 mm).
   - Design note (to be written into the report): for the first time the policy uses the robot's kinematic model from info (allowed by EVALUATION.md, but it must be stated). The end-effector position is a deterministic function of the current observation
     (q and base pose), and does not use the parking point, planning, phase or time; but it happens to be the error input of the expert IK and also the quantity measured by the success criterion,
     i.e. "using a known model for feature engineering, taking forward kinematics out of the learning problem" (corresponding to the brief's "whether extra inputs help"). If D is adopted, the main model is no longer
     "measured signals only", and the report also gives the C3 model as the result "without the robot model". Without a robot model, a model with ego_novw_ee refuses to run.

[Discussion] Structural sources of the gap to the expert (2026-11-02, post hoc, descriptive; read-only use of data/train and the existing offline evaluation files, no new simulation or training)
------------------------------------------------------------------------------------------------------------------------
1) Structure of the expert arm controller (robotnik_arm_control.arm_controller): damped pseudo-inverse IK gives qd_des, which is integrated into the reference q_des (q_des += qd_des dt,
   limited to within q ± 0.15 rad), and then a joint PD (kp 100, kd 30) plus pinocchio gravity compensation outputs the torque. q_des is an integrator that the learner cannot see;
   it lets the expert drive the EE error to 0 despite model error (equivalent to integral action). A memoryless MLP is static feedback and has no integral action.
2) Quantities in the training data (from the first 200 episodes of data/train, taking 1 in every 4, 50 in all; after nav_done; norm over the 7 joints, median):
   EE error        kp(q_des - q)   kd(qd_des - qd)
   < 5 mm          5.71 N·m        0.01 N·m
   5-10 mm         5.83            0.10
   10-20 mm        5.98            0.34
   20-40 mm        5.94            0.90
   - After reaching, kp(q_des - q) is still about 6 N·m: the integration of q_des absorbs a difference of about 6 N·m between the pinocchio gravity model and the simulator.
   - The standard deviation of the torque label is 2.2-2.8 N·m (per joint); the "label minus PD part" (the model gravity term) is 1.94 / 2.37 / 4.93 at joints 2 / 4 / 6, and the PD part
     is 3.00 / 3.66 / 6.47, i.e. the two are anti-correlated. So "pinocchio gravity compensation + learning the residual" would not shrink the output to be learned (it is larger at these joints), and is not pursued as a direction.
3) Comparison with model error: C3 (ego-novw-trig_s0) validation-set torque RMSE (norm over the 7 joints) reach_move 2.08 N·m, reach_hold 0.78 N·m
   (trained/ego-novw-trig_s0.offline.json). At 1-2 cm from the target, the "keep moving" signal kd(qd_des - qd) visible in the current observation is about 0.1-0.3 N·m,
   an order of magnitude smaller than the model error. This is consistent with the shape of extended_not_reached (median minimum error 16 mm, torque not saturated, most episodes stop near the closest point; see item 10 of the C3
   results).
4) Reading and limitations: this is an order-of-magnitude argument, not a test: only 50 training episodes and one model seed were used; the kd term is only an approximation of the memoryless visible part (acceleration and
   the change in the integral also carry information). The hypothesis it supports is "failures in the last 1-2 cm come mainly from the hidden integral state plus the precision floor of torque regression", rather than "insufficient model
   capacity"; the latter was not tested.
5) Comparability: the success threshold of 10 mm is very strict. C3-MM's reach_5cm is 92.1% on DEV, 89.2% on HARD, 92.7% on CONFIRM, and reach_2cm is 79.5 / 72.7 / 81.3%.
   Before comparing with other groups' numbers, the definitions must be aligned (threshold, closed loop or offline, whether the base is also controlled by the model, target and start distributions, time limit).

[Methodology] Step 5 pre-registration: experiment F (one round of DAgger) (written 2026-11-02, before any DEV/HARD/CONFIRM run of F; freeze record results/step5/prereg_F_frozen.txt)

- Question: when training only on states the expert itself visited (C3), the learner stops 1-4 cm from the target, circles, and creeps after reaching. If a shadow expert labels the states
  the learner visits (one round of DAgger, β = 0, i.e. the rollouts are executed entirely by C3), can success be improved?
- Single variable: the training set has the additional DAgger rows from F3 (the rest of the recipe is the same as C3). Confounds (not separated): the increase in row count also changes the number of Adam steps per epoch and the
  early-stopping timing; there is no control that adds the same number of extra expert rows.
- Main hypothesis H-F: the shadow expert's integrator keeps accumulating while the learner is stalled, so the labels carry the near-target corrective torque that is currently missing and recovery actions after deviation, and
  success therefore improves.
- Mechanism predictions (DEV, dag1 minus C3, seed mean, two-level bootstrap and Welch):
  - M1 precision: extended_not_reached decreases (both CI upper bounds < 0).
  - M2 distribution shift: circling decreases (point estimate < 0, descriptive).
  - M3 hold: held_10s increases (point estimate > 0, descriptive).
  - M4 risk: the increase in the sum of crash (tip-over) and left_or_overshot is ≤ +3 pp (point estimate).
- Competing hypotheses:
  - C1 overshoot: the shadow labels are large where the learner is stalled (the integrator leads by up to 0.15 rad, about 15 N·m); once learned, the learner overshoots or oscillates, showing up as an increase in left_or_overshot and
    crash, and success does not rise.
  - C2 label conflict: the same observation corresponds to different labels (depending on the shadow's history), the conditional mean flattens out, and there is no improvement; the expert validation-set loss rises.
  - C3 simply more data: the improvement comes from the row count and the number of training steps and has nothing to do with the learner's state (this experiment cannot separate it; recorded in the limitations).
- Verdict rule (primary metric success, unit of analysis episode, two-level bootstrap `paired_diff` and per-seed Welch, 95%):
  1. DEV: both CI lower bounds of Δsuccess > 0.
  2. DEV: M4 holds (increase in crash + left_or_overshot ≤ +3 pp).
  3. HARD: point estimate of Δsuccess > 0.
  4. CONFIRM: point estimate of Δsuccess > 0 and bootstrap lower bound > 0.
  - If all of (1)-(4) are met -> adopt dag1 as the main model. If (1) or (2) is not met -> stop, HARD and CONFIRM are not opened for F, conclusion KEEP C3.
    If (3) or (4) is not met -> KEEP C3, and report the difference between DEV and that set.
  - Mirror: both CI upper bounds < 0 on DEV -> report "one round of DAgger makes success worse".
- Secondary quantities (Holm-corrected, descriptive): reach_2cm, reach_5cm, held_10s, arm_extended_toward; success stratified by target z < 0.45 m;
  expert validation-set loss (the check for C2).
- Number of seeds: DEV 10 vs 10 (same as D; the between-seed standard deviation of C3 is about 7 pp); HARD and CONFIRM 5 vs 5 each.

### Experiment G (action chunking + temporal ensembling)
- Question: if the model predicts the next 10 actions at once and, at execution time, takes a weighted average of the overlapping predictions,
  does success improve?
- Sole variable: the output changes from the current action to a chunk of 10 segments, with temporal ensembling added at deployment; the chunk
  interval Δ is chosen on the pilot according to G5. Confound: the share of the current action in the loss drops to 1/10; chunking and
  ensembling are not tested separately.
- Main hypothesis H-G: chunk prediction and averaging make the base and arm commands consistent over time, reducing jitter and error accumulation
  in the closed loop, so base-level failures decrease.
- Mechanism predictions (DEV, G minus C3):
  - MG1: circling decreases (point estimate < 0).
  - MG2: held_10s increases (point estimate > 0).
  - MG3 (from the "hidden integrator" diagnosis; predicted unchanged): both 95% CIs of extended_not_reached lie within ±7 pp.
  - MG4: the difference between adjacent torque steps in the reach phase becomes smaller (point estimate, descriptive).
- Competing hypotheses:
  - CG1 Latency: the oldest prediction has the largest weight, the reaction slows down, and overshoot and circling increase; a large Δ is worse on the pilot.
  - CG2 Ineffective: the prediction errors of adjacent observations are highly correlated, so averaging barely reduces the error; success and the failure classes do not change.
  - CG3 The current action gets worse: the validation loss of the j = 0 segment is higher than C3's (the same quantity, directly comparable), accuracy worsens,
    and extended_not_reached increases.
  - CG4 The integrator diagnosis is wrong: extended_not_reached clearly decreases (MG3 does not hold). This would refute the statement in the Discussion that
    "the last 1-2 cm comes from hidden state".
- Rule for choosing Δ and stopping rule: G5 (frozen together with this section at freezing).

### Experiment P (output joint references + fixed PD)
- Question: if the model outputs the expert's joint references (q_des - q, qd_des) and the expert's PD + gravity compensation converts them into
  torques, can success improve?
- Sole variable: the arm's output representation (torque -> reference + fixed output layer); the base output, features, data and K are all unchanged.
  Confound: the output dimension goes from 9 to 16 (weights of 1/√2 are used to keep the base / arm shares of the loss).
- Main hypothesis H-P: the fixed layer provides exact stiffness kp, damping kd and gravity compensation, and a reference error δe causes a position error of only about δe;
  the effective stiffness of C3 near the target is learned and unknown. So the last few centimetres are more accurate and there are fewer tip-overs.
- Mechanism predictions (DEV, P minus C3):
  - MP1: extended_not_reached decreases (both 95% CI upper bounds < 0).
  - MP2: crash decreases (point estimate < 0).
  - MP3: circling is unchanged (both 95% CIs lie within ±7 pp; the base output has not changed).
  - MP4: the offline reach_hold torque RMSE is lower than C3's (median over 10 seeds, descriptive).
- Competing hypotheses:
  - CP1 Amplification: the error in e is amplified by kp = 100 (0.01 rad = 1 N·m), and the PD part itself has a larger variance than the torque (Discussion item 2), so the offline torque RMSE
    is not lower than C3's and success does not rise.
  - CP2 The integrator is still invisible: the "lead" part of e depends on history, the arm still stops 1-2 cm from the target, and extended_not_reached is unchanged.
  - CP3 Jump at the trigger: when the expert starts extending the arm, the reference of joint 6 is clipped by the joint limit and lifted from 1.0 to about 1.18 rad (e jumps by about 0.18 rad, about 18 N·m);
    this jump depends on the latched reach state; if the learner learns it flat, the start of arm extension will change. Look at arm_extended_toward and parked_no_arm.

[References] References (sources checked)
--------------------------------
- P. de Haan, D. Jayaraman, S. Levine, "Causal Confusion in Imitation Learning", NeurIPS 2019. arXiv:1905.11979.
  * Content: behaviour cloning is only discriminative regression and does not know the causal structure between the expert and the environment, so it may latch onto features that correlate with the expert's actions,
    but are not their cause (causal misidentification); the counter-intuitive conclusion is that giving the imitator more information can make it worse.
    They use targeted interventions (interacting with the environment or querying the expert) to find the correct causal structure.
  * Used in: [Methodology] input design, the motivation of experiment A.
- C. Wen, J. Lin, T. Darrell, D. Jayaraman, Y. Gao, "Fighting Copycat Agents in Behavioral Cloning from Observation
  Histories", NeurIPS 2020. arXiv:2010.14876.
  * Content: when the input includes observation history, the imitator learns to "copy the expert's previous action" (the copycat problem) instead of predicting the next action;
    they use adversarial training to remove the redundant information about the previous action from the feature representation, while keeping the information needed to predict the next action.
  * Difference from ours: our leak does not come from a history input but from the single-frame state itself: the wheels are velocity-controlled, and the measured wheel speed qd_wheel is approximately
    the previous step's wheel-speed command (copy baseline R² about 0.99, see the data-check supplement in [Methodology / Results], step 2 results 3)).
  * Used in: the reason the offline table must carry a copy baseline; the H-copycat hypothesis of experiment A (ego vs ego with v̂ and ŵ removed);
    if models with history input are added later, it must be anticipated beforehand that copycat will be more severe.

- S. Ross, G. J. Gordon, J. A. Bagnell, "A Reduction of Imitation Learning and Structured Prediction to No-Regret Online
  Learning", AISTATS 2011, PMLR 15:627-635. arXiv:1011.0686. (checked 2026-10-30: PMLR page and CMU RI page)
  * Content: the training states of behaviour cloning come from the expert, whereas at deployment the learner visits states induced by itself (violating i.i.d., errors accumulate over time);
    DAgger iteratively asks the expert for labels on the states the learner visits and aggregates the data, which can be seen as no-regret online learning, giving guarantees under the learner's own state distribution.
  * Used in: the limitations of experiment C3: C3 only re-weights the trigger frames that the expert visited and labelled, and does not query the expert on the learner's states (base parked, arm not moving).
- M. Laskey, J. Lee, R. Fox, A. Dragan, K. Goldberg, "DART: Noise Injection for Robust Imitation Learning", CoRL 2017,
  PMLR 78. arXiv:1703.09327. (checked 2026-10-30: arXiv and mlanthology pages)
  * Content: noise is injected into the expert's control during demonstration, so that the data cover the states the learner's errors would take it to; the noise magnitude is set according to the trained policy's error;
    off-policy, with no need to query the expert on the learner's trajectories.
  * Used in: [Methodology] data collection design (the idea of noisy episodes); the limitations of experiment C3 (C3's jitter on the arm qd is only on the input and does not change the expert trajectory).

- T. Z. Zhao, V. Kumar, S. Levine, C. Finn, "Learning Fine-Grained Bimanual Manipulation with Low-Cost Hardware", Robotics: Science and
  Systems XIX (RSS 2023), paper 16. arXiv:2304.13705. (checked 2026-11-03: arXiv abstract page and roboticsproceedings.org/rss19/p016)
  * Content: ACT (Action Chunking with Transformers). The policy predicts the next k actions at once (action chunking); at execution it is queried at every step and takes an exponentially weighted average of the
    overlapping predictions that point to the same time step (temporal ensembling, the oldest prediction gets the largest weight); a CVAE handles the multimodality of human demonstrations; the actions are joint-position targets, executed by a low-level
    PD controller (50 Hz).
  * Used in: the motivation of step 6's experiments G (chunking + temporal ensembling) and P (position reference + fixed PD); G's failure (weighted averaging introduces
    delay under 1 kHz torque output) and P's result; the reasons for not adopting a CVAE (the expert is a deterministic script) or a transformer.

- C. Wen, J. Lin, J. Qian, Y. Gao, D. Jayaraman, "Keyframe-Focused Visual Imitation Learning", ICML 2021, PMLR 139:11123-11133.
  arXiv:2106.06452. (checked 2026-11-06: proceedings.mlr.press/v139/wen21d.html and arXiv abstract page)
  * Content: a follow-up on the copycat problem: in demonstrations, the frames where the expert's action changes (keyframes / changepoints) are swamped in behaviour cloning by many frames that "continue the previous action",
    and they weight these frames by the probability of an action changepoint (keyframe-focused loss), outperforming baselines on MuJoCo image control and CARLA driving.
  * Relation to ours: the trigger-frame copy (C3 / K 144) is a special case of it: it only weights one transition frame per episode (the first frame after nav_done), selected by a label
    (the first row of the trailing zero-wheel-speed segment) rather than by a learned changepoint probability, and adds jitter to the input; Rodrigo's control shows that adding only loss weight
    (K+1, no jitter) reaches less than the copies (84% vs 92%).
  * Used in: report III-C (the positioning of the device, one sentence added in draft 4).
